# 주식계좌 원금대비손익율 그래프

## 요구사항과 완료조건

- `/work/totalstock`에서 `월별 정보 → 계좌별 전체 이력 정보 → 원금대비손익율(그래프) → 입출금내역` 순서로 탭을 제공한다.
- 그래프의 세로 중앙에 원금과 같은 상태를 의미하는 손익 기준선 `0%`를 표시한다.
- 상단의 `일/월/년`과 하단의 `1개월/3개월/6개월/1년/3년` 버튼으로 표시 단위와 기간을 선택한다.
- 그래프의 점 표시는 생략한다. 마우스·터치 위치에 가장 가까운 실제 확인일의 날짜, 원금, 평가금, `손익금(원금 대비 증감률)`을 그래프 바로 위 왼쪽에 작게 표시한다. 키보드 좌우 화살표와 Home/End도 지원한다.
- 정보 행과 조회기간 버튼은 그래프 위아래에 각각 8px 간격으로 배치하고 화면 높이를 채우는 여백을 만들지 않는다.
- 빈 데이터, 단일 확인일, 원금 0 이하, 모바일 카드 배치를 처리한다.

## 금액과 날짜 기준

- 원금: 선택 계좌의 해당 확인일까지 누적 입금에서 누적 출금을 뺀 금액이다. 기존 계좌별 전체 이력의 계산 결과를 재사용한다.
- 평가금: 해당 확인일에 입력된 선택 계좌의 평가금 합계다. 확인 이력이 없는 날짜의 평가금을 새로 추정하지 않는다.
- 손익금: `평가금 - 원금`이다. 그래프 손익율은 `(평가금 - 원금) / 원금 * 100`이며 원금과 같으면 0%, 평가금이 원금보다 10% 많으면 +10%다.
- 정보 행의 손익은 `+1,270,000원 (+12.70%)`, `-1,030,000원 (-10.30%)`처럼 표시한다. 수익은 붉은색, 손실은 파란색으로 구분한다.
- API의 `principalRatio`는 기존 100% 기준 계약을 유지한다. 화면은 이 값에서 100을 뺀 증감률을 표시한다.
- 원금이 0 이하이면 비율은 `null`이고 화면에는 `계산 불가`를 표시한다. 이 날짜에서 선을 끊는다. 양수 원금에 평가금이 0이면 손익율은 -100%다. 단일 확인일은 점 대신 짧은 선으로 위치를 표시한다.
- 일은 실제 확인일별 값을 사용한다. 월·년은 조회기간 안에 있는 각 월·년의 마지막 확인일 스냅샷을 사용한다. 기간별 금액이나 비율을 합산·평균하지 않는다.
- 기본 선택은 일·3개월이다. 조회기간의 끝은 최신 확인일이며 시작은 최신 확인일에서 선택한 개월 수를 뺀 날짜다. 말일은 대상 월의 마지막 날짜로 보정한다.
- 선택 기간이 데이터보다 길면 최초 확인일부터 표시한다. 날짜 사이 간격은 실제 경과 일수를 따른다.
- 표시 단위와 기간 변경은 브라우저에서 처리하므로 API를 추가로 호출하지 않는다.

## 영향범위와 API 계약

- 프론트: 탭, 독립 그래프 컴포넌트, 날짜·기간 유틸, 응답 타입과 정규화, 모바일 스타일이다. 신규 의존성을 추가하지 않는다.
- 백엔드: 기존 `StockAccountHistoryService`가 계산한 전체 확인일 목록으로 그래프 응답을 만든다. 매퍼와 SQL, DB 스키마, 배치를 추가하지 않는다.
- 배포: 프론트와 백엔드를 함께 반영해야 한다. 기존 `GET /api/work/stock-account-history`의 계좌 조건과 인증을 그대로 사용한다.
- 응답에 `profitGraphPointList`를 추가한다. 이 목록은 확인일 오름차순이며 이력 표의 50건 페이지와 월초·월말 보기 조건에 영향을 받지 않는다.

| 필드 | 형식 | 의미 |
|---|---|---|
| `checkDt` | 문자열 | 실제 확인일, `yyyy-MM-dd` |
| `principalAmt` | 숫자 | 확인일까지의 선택 계좌 누적 원금 |
| `checkAmt` | 숫자 | 확인일의 선택 계좌 평가금 합계 |
| `principalRatio` | 숫자 또는 null | 원금 100% 기준 비율, 소수 둘째 자리 |

## 집계 테이블 판단

2026-10-13에 지정된 조회 전용 계정으로 실제 DB를 확인했다. 평가금 원천은 311행·63일, 입출금 원천은 120행·51일, 활성 계좌는 5개였다. 최초 확인일은 2026-07-08, 최신 확인일은 2026-10-13이었다.

기존 원천 SQL의 `EXPLAIN ANALYZE`에서 평가금 조회·정렬은 약 3.4ms, 입출금 일별 집계는 약 0.2ms였다. 클라이언트 왕복 포함 단일 측정은 각각 21ms와 8ms였다. 운영 동시 부하나 장기 데이터 증가에 대한 부하 테스트 결과는 아니다.

현재 데이터 규모에서 추가 쿼리 없이 기존 결과를 재사용할 수 있으므로 집계 테이블·DDL·소급 쿼리·Node 배치가 필요하지 않다. 데이터가 크게 증가하면 기존 전체 이력 API의 원천 조회와 응답 크기를 함께 재측정한다.
